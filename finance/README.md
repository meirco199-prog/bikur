# ניהול הכנסות והוצאות — עסקי ופרטי

אפליקציית ווב מלאה לניהול פיננסי חודשי, בעברית ו-RTL, מותאמת למחשב ולמובייל.
עובדת בפועל: כל כפתור מבצע פעולה אמיתית על הנתונים.

**כתובת:** `/finance/` (מוגשת מ-GitHub Pages, ללא שלב build)

---

## 1. ארכיטקטורה

האפליקציה בנויה בארבע שכבות מופרדות. שכבה עליונה מכירה רק את זו שמתחתיה.

```
┌─────────────────────────────────────────────────────────┐
│  screens/  — מסכים. מרכיבים ממשק, לא מחשבים כסף        │
├─────────────────────────────────────────────────────────┤
│  ui/       — רכיבים לשימוש חוזר, גרפים, טפסים, ייצוא   │
├─────────────────────────────────────────────────────────┤
│  domain/   — חישוב דטרמיניסטי: סכומים, ממוצעים, תחזית  │
│  importer/ — פירסור קבצים, סיווג, כפילויות             │
├─────────────────────────────────────────────────────────┤
│  core/     — שכבת נתונים, סכימה, עזרים                  │
└─────────────────────────────────────────────────────────┘
```

**כלל הברזל:** כל סכום, יתרה, אחוז, ממוצע ותחזית מחושבים ב-`domain/finance.js`
בקוד דטרמיניסטי בלבד. AI, אם וכאשר יופעל, משמש רק לזיהוי בתי עסק ולניסוח משפטים —
לעולם לא לחישוב כספי.

### למה לא Next.js

הריפו הזה מתפרסם ישירות מ-`main` דרך GitHub Pages ללא שלב build (ראו `CLAUDE.md`).
לכן האפליקציה נכתבה כ-ES Modules טהורים, מודולריים ובלי bundler — היא עולה לאוויר
ברגע שהיא נדחפת. **שכבת הנתונים בנויה כך שהמעבר ל-Supabase הוא שינוי שורה אחת**
(ראו סעיף 3), וסכימת ה-PostgreSQL המלאה כבר כתובה ב-`supabase-schema.sql`.

## 2. מודל הנתונים

אין טבלה נפרדת לכל חודש. השיוך החודשי הוא שדה (`month`) עם אינדקס.

| ישות | תפקיד |
|------|-------|
| `Transactions` | הטבלה המרכזית — 36 שדות לכל תנועה |
| `Categories` | קטגוריות פר מרחב וכיוון, עם צבע, אייקון וסדר |
| `Accounts` | חשבונות וכרטיסים — **4 ספרות אחרונות בלבד** |
| `Budgets` | תקציב לקטגוריה, כללי או ייעודי לחודש |
| `MerchantRules` | חוקי סיווג — נלמדים מהחלטות המשתמש |
| `Imports` | קבוצת ייבוא: קובץ, תקופה, תוצאות |
| `Months` | מטא-דאטה: חודש סגור, ממה שוכפל |
| `Settings` | העדפות, סינונים שמורים |
| `AuditLog` | תיעוד שינויים משמעותיים |

### שלוש החלטות מודל שקובעות את נכונות החישוב

1. **הסכום תמיד חיובי**, והכיוון נשמר ב-`direction`. אין סכומים שליליים
   שמסתננים לחישוב בטעות.
2. **שלושה דגלי אי-הכללה**: `internalTransfer` ו-`isSettlement` מוציאים תנועה
   מכל חישובי ההכנסות וההוצאות. `isRefund` מקזז — זיכוי מקטין את ההוצאה
   בקטגוריה במקום להיספר כהכנסה.
3. **תשלומים נרשמים חודשית**. עסקה של 6,000 ₪ ב-6 תשלומים נרשמת כ-1,000 ₪
   בכל חודש, עם `installment: { current, total, totalAmount }`.

## 3. מעבר ל-Supabase

1. להריץ את `supabase-schema.sql` (יוצר טבלאות, אינדקסים, RLS ותצוגות עזר).
2. לייצא גיבוי מהאפליקציה (הגדרות ← הורדת גיבוי מלא) ולייבא לטבלאות.
3. ב-`js/core/store.js` להחליף שורה אחת:

```js
// לפני
export const store = createStore();

// אחרי
export const store = createStore(new SupabaseAdapter({ client, userId }));
```

`SupabaseAdapter` כבר כתוב באותו קובץ ומממש את אותו ממשק
(`load / persist / insert / update / remove / bulk`). שאר האפליקציה לא משתנה.

## 4. צינור הייבוא

```
קובץ → זיהוי קידוד → זיהוי כותרות → שורות גולמיות
     → סיווג (חוקים → היסטוריה → חוקי בסיס → דמיון)
     → זיהוי חיוב מרוכז / העברה / זיכוי
     → זיהוי כפילויות
     → מסך אישור  ←── שום דבר לא נשמר לפני כן
     → שמירה + למידת חוקים
```

### פירסור

- **קידוד**: דוחות בנק ישראליים מגיעים לא פעם ב-`windows-1255`. המערכת מזהה
  ומפענחת אוטומטית.
- **כותרות**: זיהוי לפי 15 קבוצות דפוסים בעברית ובאנגלית
  (`תאריך עסקה`, `תאריך חיוב`, `שם בית עסק`, `חובה`/`זכות`, `אסמכתא`, ועוד).
- **עמודות חובה/זכות** נתמכות לצד עמודת סכום יחידה עם סימן.
- **PDF**: חילוץ טקסט עם מיקומים וקיבוץ לשורות לפי קו Y.
- **חילוץ**: 4 ספרות כרטיס, מספר תשלומים (`תשלום 2 מתוך 6`, `3/12`), מטבע מקור.
- שורות סיכום (`סה״כ`, `יתרת פתיחה`) מסוננות אוטומטית.

### סיווג, לפי סדר עדיפות יורד

| # | מקור | ביטחון |
|---|------|--------|
| 1 | חוק שנלמד מהמשתמש | 94–99% |
| 2 | היסטוריה — אותו בית עסק סווג בעבר | 72–97% |
| 3 | חוקי בסיס מובנים (~120 בתי עסק ישראליים) | 84–92% |
| 4 | דמיון מחרוזות להיסטוריה | 55–82% |
| 5 | ללא זיהוי → קטגוריית ברירת מחדל | 30% (דורש בדיקה) |

מתחת ל-70% התנועה מסומנת **"דורש בדיקה"** ומוצגת ראשונה במסך האישור.
הכרעת עסקי/פרטי מבוססת על החשבון שאליו שויך הקובץ + מילות מפתח;
כשהוודאות נמוכה מ-65% מוצג **"דרוש אישור"**.

### למידה

כשהמערכת אינה בטוחה היא שואלת: *"לאיזו קטגוריה לשייך את מחסני השוק?"*
הבחירה נשמרת כחוק (`מחסני השוק → קניות בסופר`) והופכת לאוטומטית בייבוא הבא.
הדפוס נגזר מהחלק המשמעותי בשם, ללא מספרי סניף — כך ש"רהיטי בן דוד בע״מ"
מזהה גם את "רהיטי בן דוד סניף חולון". כל החוקים ניתנים לעריכה ולמחיקה.

### זיהוי כפילויות — חמש שכבות

| בדיקה | רמה |
|-------|-----|
| מזהה חיצוני זהה באותו חשבון | כפילות ודאית |
| שורה זהה פעמיים באותו קובץ | כפילות ודאית |
| תאריך + סכום + בית עסק + חשבון | ודאית / סבירה |
| סכום זהה בטווח 3 ימים + בית עסק דומה | סבירה |
| אותו חודש + אותו סכום + אותו בית עסק | ייתכן שקיים |

כפילות אינה מיובאת כברירת מחדל, אך אפשר לאשר ידנית "ייבא בכל זאת".

### חיוב אשראי מרוכז

אם בדף העו״ש מופיע `ישראכרט 12,450 ₪` וגם יובאו העסקאות עצמן —
החיוב המרוכז מזוהה, מסומן `isSettlement`, מקושר לכרטיס **ואינו נספר כהוצאה נוספת**.

## 5. מה נבדק

הבדיקות רצו בדפדפן אמיתי (Chromium), לא רק ביחידות:

- 13 המסכים נטענים ללא שגיאת JavaScript.
- הוספה, עריכה, מחיקה וביטול מחיקה (Undo) של תנועה.
- ייבוא CSV מלא: 9 שורות → חיוב מרוכז זוהה, העברה פנימית זוהתה,
  משכורת כפולה **לא** יובאה פעמיים, 8 תנועות נשמרו.
- מנגנון הלמידה: סיווג ידני → חוק נוצר → ייבוא חוזר סווג אוטומטית ב-94%.
- שכפול חודש כולל קידום מספר תשלום.
- יצירת תקציב, קטגוריה וחשבון; ייצוא CSV; גיבוי JSON; מצב כהה נשמר.
- מובייל 390px: אפס גלישה אופקית בכל המסכים.

חישובי הליבה נבדקו גם ישירות: זיכוי מקזז הוצאה, העברות וחיובים מרוכזים
אינם נספרים, ואחוזי ההשוואה מדויקים.

## 6. פרטיות ואבטחה

- הנתונים נשמרים **במכשיר בלבד** (localStorage). אין שרת ואין העלאה.
- קבצי הדוחות מעובדים **בדפדפן**. שום מסמך לא נשלח לשירות חיצוני.
- **4 ספרות אחרונות בלבד** של כרטיס. מספר חשבון מלא לא נשמר כלל.
- הקובץ המקורי נמחק אחרי העיבוד (ניתן לשינוי בהגדרות).
- אין scraping ואין חיבור לא רשמי לשירות פיננסי. סנכרון ארנק — רק דרך API
  רשמי עם אסימון קריאה. אין להזין סיסמאות בנק.
- לכל תנועה מתועד מקור (ידני / ייבוא / שכפול / חוזרת) + יומן ביקורת לשינויים.
- מחיקת כל נתוני המשתמש זמינה בהגדרות, עם הצעת גיבוי לפני.
- בסכימת ה-PostgreSQL: Row Level Security מלא — כל שורה נגישה לבעליה בלבד.
